# tero: сводная спека (HUD + пульт + отказоустойчивость + agy)

Дата: 2026-10-22. Три части, каждая самостоятельна; здесь порядок и стыки.

| # | Часть | Что даёт | Источник |
|---|---|---|---|
| 0 | HUD (раунд 0) | окно прогона на компе, пишет `state.json`/`stream.jsonl` | часть A ниже |
| 1 | Ядро пульта | точки решения, `answer/resume`, пульс, ретранслятор, телефон (PWA), лимиты | часть B ниже |
| 2 | Отказоустойчивость, `agy`, экзамен судей | снимки в refs, `judge_pending`, провайдер `agy` | часть C ниже |

**Порядок:** HUD → ядро пульта (общий `state.json`) → отказоустойчивость → ретранслятор и телефон. Отказоустойчивость
добавляет в `state.json` статус `judge_pending` и поля `snapshot_ref`/`base`; HUD и пульт обязаны его показывать.
**Модели:** судья по умолчанию — не из семьи исполнителя; `agy` (Gemini 3.8 Flash, Claude 4.6) и `opencode` (GLM 5.3
flash) — рабочие кандидаты; Gemini 3.1 Pro в `agy` не обнаружен.
**Ограничения:** не менять tero посреди прогонов «Двора»; всё в отдельной копии; red→green на каждый сбой.

## Единые решения (волны 1–2 критиков; при расхождении с частями ниже главнее они)

Пометка *(моё)* — решение Claude, его можно оспорить. Критики: Gemini (`agy`, gemini-3.8-flash-high) и GLM 5.3 flash.

1. **Один enum статуса** в `state.json`: `starting | running | waiting_human | waiting_agent | waiting_limit | judge_pending | done | stopped`.
   `judge_pending` — живое ожидание, не терминальный стоп: `tero wait` возвращает код 3, HUD рисует «⏸ код ждёт ревью»,
   пульт даёт кнопки. «3 сбоя судьи» = принудительная точка решения.
2. **Один вход восстановления:** `tero resume` смотрит статус (краш, ожидание, «с судьи на ref»). Отдельный флаг
   `tero go --resume` из части C не вводить.
3. **Снимок (часть C, §0) — общий механизм ядра.** Перед ЛЮБЫМ откатом или kill (стоп с телефона, сторож, `skip`,
   `retry`, автопилот) вызывается один и тот же снимок в `refs/tero/...`. Версия части B «`git write-tree` с
   неотслеживаемыми» заменяется на снимок через временный `GIT_INDEX_FILE` (иначе новые файлы не попадают в sha).
4. **Роль `model judge` отклонять** при приёме ответа (пульт, агент, автопилот); на телефоне судья не в списке.
   Менять можно `player` и `tester`. Судья — из другой семьи, чем исполнитель.
5. **Автопилот и `judge_pending`:** только «позвать судью снова» (в бюджет 3), затем `skip` в долг.
   «Принять вручную» и «отклонить» — только человек.
6. **Порядок старта `run()`** (единый для A и B): git-репо → `exclude_tero()` → `flock` на `.tero/run.lock` →
   папка прогона, `state.json: starting`, HUD → проверки (дерево, провайдеры, план, тесты).
7. **`--detach` и pid:** `state.json` пишет финальный процесс-владелец после форка; `caffeinate` через `exec` (pid не
   меняется); родитель `state.json` не трогает. Тест: HUD после detach не мигает «оборвался».
8. **Внутри процесса-владельца** один `threading.Lock` на `state.json` и git-операции; сторожевой поток только
   ставит флаг, откат делает главный поток.
9. **Аренда агента** хранит pid сессии агента; смерть pid = аренда недействительна, `wake_command` срабатывает сразу.
   Промпт `wake_command` фиксирован, действия только `retry|skip|stop` с `--why`, без свободного текста.
10. **Ретранслятор:** ключ записи `run_id` (+ `machine_id`), PWA показывает список активных прогонов. Чтение
    состояния только по токену; фильтр секретов смотрит подстроки (`sk-`, `AKIA`, hex/base64), не только строки.
    `phone_text_answers: false` по умолчанию: с телефона кнопки `more|skip|retry|stop`; текст — явным флагом и с санитизацией.
11. **«+1 прогон» в HUD** требует реестра прогонов в `~/.tero/registry/` (pid, путь к `state.json`), пишут все запуски.
    Нет реестра → «+1» не делаем.
12. **Порядок работ:** ядро состояний (`state.json`, enum, flock) делается ДО HUD или вместе с ним, чтобы HUD не переделывать *(моё)*;
    затем отказоустойчивость (до ретранслятора и телефона); часть C «после Двора» значит «не менять tero посреди
    прогонов», а не «в конец очереди».
13. **HUD по умолчанию только читает.** Действия из HUD (ответ на вопрос) — отдельный раздел ядра пульта: те же
    файлы `inbox/`, тот же список действий, что на телефоне; до тех пор кнопок нет, анти-цель HUD остаётся.
14. **Долг в HUD:** финал с долгом показывается «⚠ сдано с долгом N» (поле из `state.json`), не «✓».
15. **Приёмка HUD №1 (фокус)** — эксперимент на 1 рабочий день: если `pywebview`/`pyobjc` не дают окно без
    кражи фокуса, окно открывается свёрнутым в фоне, прогон не страдает.

# ЧАСТЬ A. HUD

# tero HUD: окно прогона на компе

Раунд 0 — делается до всего из [спека пульта](2026-10-21-tero-pult-design.md).

## Зачем

Сейчас прогон tero виден только как поток строк в терминале. Чтобы понять, на какой фазе он, кто сейчас работает и что сказал судья, надо листать консоль. Темирлан хочет, чтобы при запуске tero на компе само открывалось маленькое окно поверх всего: одним взглядом видно, сколько фаз сдано, что идёт сейчас и что там происходит. Если интересно — развернуть и читать живые логи игроков.

Второе зачем: HUD — первый кирпич пульта. Файл состояния, который tero начинает писать для HUD, — это начало того `state.json`, на котором потом строится ядро пульта, а вёрстка HUD потом переезжает на телефонную страницу.

## Цели

- `tero go` на компе сам открывает HUD. Если окно уже открыто — переиспользует его, а не плодит новые.
- **Свёрнутый вид** — горизонтальная плашка поверх всех окон:
  - слева круг: сектор = фаза плана. Зелёный — сдана, жёлтый — идёт сейчас, красный — ещё не сделана;
  - в центре круга иконка момента: 🛠 player, ⚖️ judge, 🧪 tester, ⏱ гоняются тесты, ❓ стоп (нужен человек), ✓ всё сдано;
  - справа: «Фаза N/M · раунд R · время фазы», роль и модель («player · opus»), одна-две строки о том, что роль делает сейчас.
- **Развёрнутый вид** (по клику на круг или кнопку):
  - сверху та же строка, что в свёрнутом, и «свернуть»;
  - слева список всех фаз с названиями и цветными точками; клик по фазе показывает её лог;
  - в центре живой лог вкладками: всё / player / judge / tester / тесты;
  - внизу «последнее сообщение»: последний вердикт судьи (SHIP / NO_SHIP, первая находка с `файл:строка`), итог tester'а или причина стопа.
- Строка «что делает» берётся из того, что роль сама выдаёт по ходу: последний текст роли, если его нет — последний вызов инструмента (`Read src/parse.py`, `Bash pytest -q`). Никакой отдельной модели-пересказчика.
- `tero hud` — открыть HUD для текущего или последнего прогона в этом репо вручную.

Макеты, которые Темирлан подтвердил: `.superpowers/brainstorm/*/content/hud-collapsed.html` и `hud-expanded.html` (в `.gitignore`; суть описана выше, они только для глаза).

## Не цели (в раунде 0)

- **Отвечать из HUD.** В tero пока нет точек решения: любой стоп завершает прогон (код 2). HUD показывает ❓ и причину стопа, но кнопок ответа нет. Они появятся вместе с ядром пульта.
- Прогон на удалённой машине (Muse VM и т.п.). HUD — только когда tero идёт на этом компе. Удалённые прогоны — телефон и пульт.
- Лимиты, телефон, пуши, несколько прогонов в одном окне.
- Управление прогоном из HUD (стоп, пауза).

## Анти-цели (провал, даже если «работает»)

- HUD хоть как-то влияет на прогон: упал, завис, закрыт, не установлен — прогон идёт как шёл, без задержек и без новых ошибок.
- Окно при каждом запуске крадёт фокус клавиатуры, пока Темирлан печатает в другом окне.
- После десяти запусков на экране десять окон.
- tero без HUD (сервер, CI, SSH) начинает требовать GUI или новые зависимости.
- В HUD видно то, чего нет в прогоне (выдуманный прогресс), или он показывает «работает», когда прогон уже умер.

## Как это устроено

```
tero go ──пишет──▶ .tero/runs/<run>/state.json   (снимок: статус, фазы, роль, вердикт)
   │              .tero/runs/<run>/stream.jsonl  (живой лог ролей и гейтов)
   │              .tero/runs/<run>/ledger.jsonl  (как сейчас)
   │
   └─Popen, не ждёт──▶ tero hud  ──читает файлы раз в ~1 с──▶ окно
```

HUD — отдельный процесс. Он только читает файлы прогона. tero ничего не ждёт от HUD и не знает, жив ли он.

### Порядок старта в `run()` (обязательный)

Сейчас `run()` (`src/loop/run.py`) делает проверки, и только после всех — `exclude_tero()` и `new_run_dir()`. Для HUD порядок меняется так:

1. Проверка, что это git-репо (ошибка — код 1, HUD не открывается: показывать нечего).
2. **`exclude_tero()` — до любой записи в `.tero/`.** Иначе первый же `state.json` в свежем клоне делает дерево «грязным» (`?? .tero/`), проверка чистоты валит старт, `exclude_tero` никогда не вызывается — и так на каждом запуске, причём и с `--no-hud`, ведь `state.json` пишется всегда.
3. Создать папку прогона и `state.json` со `status: starting`; запустить HUD (см. ниже).
4. Дальше стартовые проверки как сейчас (провайдеры, грязное дерево, план, стартовые тесты). Каждый шаг обновляет «что делает» в `state.json` («проверяю провайдеров…», «стартовые тесты: pytest -q…» со временем начала). Провал → `status: stopped` с причиной и текстом, код 1 как сейчас.
5. `ledger.jsonl` создаётся, как сейчас, только когда прогон реально стартовал. `history()` уже пропускает папки без ledger — поэтому несостоявшиеся старты в `tero history` не попадают, а HUD их видит.

«Последний прогон» для `tero hud` — самая свежая папка в `.tero/runs/` с `state.json` (не через `history()`). Ошибки до `run()` (план не найден в `cli_entry`, плохой конфиг) HUD не открывают — они и так мгновенно видны в терминале.

`nothing_to_do` (всё уже сдано) — HUD показывает полностью зелёный круг и «нечего делать».

### Что пишет tero

**`state.json`** — снимок, атомарно (временный файл + rename). Пишет только процесс прогона, при каждом изменении снимка: шаг старта, старт фазы, смена роли, старт и итог гейта, вердикт, итог tester'а, сдача, стоп, конец. Поля (как минимум):
- `status`: `starting` / `running` / `done` / `stopped`; при `stopped` — причина (`user`, `stuck`, `fuse`, `provider_unavailable`, `secrets`, как сейчас, плюс провалы старта: грязное дерево, красные стартовые тесты, провайдер не готов, нет чекбоксов) и человеческий текст;
- `pid` и **время старта этого процесса** (из `psutil`), время последней записи;
- план, список фаз (название, `done` / `active` / `todo`); фазы, сданные до этого прогона, — `done`, помечены «в прошлом прогоне». На `starting`, пока план не прочитан, фаз нет — круг серый;
- текущая фаза, раунд, время старта фазы;
- текущая роль (`player` / `judge` / `tester` / `gate`), провайдер, модель, время старта шага;
- последний вердикт судьи: `verdict`, число blocking, первая находка (проблема, файл, строка) — **из уже провалидированного JSON судьи в `_judge`** (`src/loop/phase.py`), не из ledger и не парсингом артефактов; так же последний итог tester'а и гейта (ok / код выхода / хвост вывода ~40 строк);
- шаг старта (на `starting`).

Записи `state.json` — в тех же точках `phase.py` / `run.py`, где сейчас пишется `ledger.event` или печатается строка статуса. Ошибка записи `state.json`/`stream.jsonl` (диск, права) **не роняет прогон**: одна строка предупреждения в консоль, дальше без HUD-файлов.

Ядро пульта потом расширяет этот же файл своими полями (вопрос, журнал решений, бюджет, lease, пульс), не ломая эти.

**`stream.jsonl`** — по строке на событие, дописывается целой строкой: время, фаза, раунд, роль, тип, текст. Типы:
- `tool` — вызов инструмента (то, что сейчас печатает `_activity` в `_collect_text`, `src/loop/agents.py`), сразу как пришёл;
- `text` — текст роли (~300 символов), **по каждому сообщению провайдера, как пришло**, всегда, не только при `--verbose`; в консоль — как сейчас. Если провайдер отдаёт текст только финальным сообщением — живыми будут только `tool`-строки, это честно;
- `gate_start` / `gate` — гейт начат / итог (ok, код, хвост вывода). Вывод тестов по ходу **не** стримится (сейчас `run_all` захватывает его целиком, `src/loop/gates.py`) — в раунде 0 это не меняем;
- `verdict`, `tester`, `ship`, `stop`, `start_step`.

**«Что делает»** HUD вычисляет сам из хвоста `stream.jsonl` (последний `text` текущей роли, иначе последний `tool`), а не берёт из `state.json` — так строка живая без частых перезаписей снимка. Для гейта — «⏱ тесты идут 2:41» (таймер от `gate_start`), для стопа — причина. Рядом всегда «последнее событие N с/мин назад» — если роль молчит 10 минут, это видно, а не замаскировано старой фразой.

### Как HUD читает файлы

- `state.json` — перечитывает целиком (он маленький); не распарсился — держит прошлый снимок.
- `stream.jsonl` — хвост по смещению: читает только новое с прошлого раза, недописанную последнюю строку (без `\n`) откладывает до следующего чтения, битую строку пропускает. Файл стал короче смещения (ротация/обрезка) — читает заново с начала.
- Окно держит в памяти ограниченный хвост лога (несколько тысяч строк), а не весь файл.

### Как HUD понимает «умер»

`status` = `starting`/`running`, но процесса с этим `pid` **и тем же временем старта** нет → «прогон оборвался» (красным, ❓). Переиспользованный системой pid так не обманет. Зависание (процесс жив, событий нет) HUD не диагностирует — он только честно показывает «последнее событие 14 мин назад». Настоящий пульс и «завис» — в ядре пульта, HUD тогда перейдёт на его протокол.

### Окно

- Python, как tero: `pywebview` (на маке — WKWebView). Страница — **один самодостаточный HTML** (CSS/JS внутри), загружается через `html=`, не через локальный URL: иначе pywebview поднимает свой HTTP-сервер на случайном порту и macOS начинает спрашивать про входящие подключения. Данные странице — через мост `js_api`. У процесса HUD нет слушающих сокетов.
- Окно без рамки, поверх всех окон, перетаскивается мышью, запоминает позицию и вид (свёрнутый/развёрнутый) между запусками.
- **Открывается без кражи фокуса.** Флага pywebview может не хватить: по чтению кода (судья GLM, pywebview 6.x) cocoa-бэкенд при показе активирует приложение. Поэтому **первая задача плана — спайк**: окно поверх всех, пока печатаешь в другом приложении. Не держит — через pyobjc (на нём pywebview и так стоит): процесс HUD как accessory-приложение без иконки в доке, окно не активирующее (non-activating panel) или показ без активации. Только если и это не выходит — вернуться к Темирлану с вариантом «открывается свёрнутым в фоне».
- **Одно окно на машину.** Новый `tero go` или `tero hud` не открывает второе окно, а переключает существующее на свой прогон. Если в это время идёт ещё прогон (другое репо), окно показывает маленькую метку «+1 прогон» — клик переключает. Несколько прогонов одновременно на экране — не цель.
- После конца прогона окно остаётся с итогом (всё зелёное ✓ или стоп ❓ с причиной), пока его не закроют или не стартует новый прогон.
- Клик по фазе, сданной в прошлом прогоне, — «сдана в прошлом прогоне» и путь к его папке; лог чужого прогона в раунде 0 не подтягиваем.
- Тёмная тема, как в макетах.

### Когда `tero go` открывает HUD

**Сразу при запуске** (шаг 3 порядка старта), а не когда начнётся первая фаза: Темирлан сказал «каждый раз, когда запускаешь теро». Если есть интерактивное меню настроек — после него (меню — до `run()`).

Кто запустил tero — человек в терминале или агент-хозяин (Claude Code и т.п.) на этом же маке — не важно: `--no-menu` и отсутствие TTY HUD **не** выключают.

Правило запуска, по порядку:
1. `--no-hud` или `hud: false` в конфиге → не запускать.
2. Не macOS (в раунде 0) → не запускать.
3. SSH-сессия (`SSH_CONNECTION`/`SSH_TTY` в окружении) → не запускать.
4. Иначе — запустить `tero hud --run <папка>` через `Popen` и **не ждать**: новая сессия (`start_new_session=True`, Ctrl+C прогона его не трогает), stdin из `/dev/null`, stdout/stderr — в `.tero/hud.log`, не в консоль прогона. `pywebview` импортируется только в процессе HUD, не в tero.
5. Если HUD не смог (нет `pywebview`, нет доступа к оконному серверу, упал) — он тихо умирает с записью в `.tero/hud.log`; tero об этом не узнаёт. Единственное исключение для подсказки: если tero дёшево видит, что `pywebview` не установлен (`importlib.util.find_spec`, без импорта), — одна строка «HUD: pip install tero[hud]» в консоль, и HUD не запускается.

Так ошибка в определении GUI стоит только пустого процесса, который сам умирает, — прогон от неё не страдает и не ждёт.

`pywebview` — необязательная зависимость (`pip install tero[hud]`); сам tero без неё работает как раньше.

## Решения, которые принял я (Claude), не Темирлан

- `pywebview` + веб-вёрстка, а не нативный Swift: тот же язык, что tero, и вёрстка переедет на телефон. Нативное было бы чуть красивее, но это второй язык и вторая вёрстка.
- Файлы, а не сокет/HTTP между tero и HUD: HUD не может повлиять на прогон, можно открыть HUD для уже идущего или законченного прогона, и это тот же `state.json`, что нужен пульту.
- `stream.jsonl` отдельно от `ledger.jsonl`: ledger — редкие важные события, stream — частый шум для глаз.
- Строка «что делает» — из текста самой роли, без модели-пересказчика (деньги и задержка); HUD считает её из хвоста лога.
- Вывод тестов по ходу гейта не стримим — только таймер и итог с хвостом.
- Окно не крадёт фокус (спайк первым), одно на машину, второй прогон — меткой «+1».
- Несостоявшиеся старты видны в HUD, но не в `tero history`.
- Только локальные прогоны и только macOS; ответов из HUD нет до ядра пульта.
- HUD открывается и тогда, когда tero запустил агент на этом маке (`--no-menu`, без TTY): ты сказал «каждый раз». Не хочешь окна — `--no-hud` или `hud: false`.

## Оставлено строителю

- Точный формат `state.json` и `stream.jsonl`, имена полей.
- Как именно держать «одно окно» (lock-файл, сокет — что надёжнее с pywebview) и как окно узнаёт о новом прогоне.
- Размеры, шрифты, анимация круга, иконки (эмодзи из макета или свои).
- Как тестировать: запись `state.json`/`stream.jsonl`, порядок старта, правило запуска, чтение хвоста — юнит-тестами; окно — демо-прогоном на фейковых файлах и ручной проверкой.
- Ротация/обрезка `stream.jsonl` на очень длинных прогонах.

## Приёмка

1. Спайк: окно HUD поверх всех появляется, пока печатаешь в другом приложении, и ни один символ не теряется.
2. `tero go` на маке по реальному плану открывает плашку, не забирая фокус; круг, иконка, роль и строка меняются по ходу прогона, совпадая с консолью; на гейте тикает таймер.
3. Разворот показывает все фазы, живой лог по вкладкам и последний вердикт судьи с `файл:строка`.
4. Закрыть окно посреди прогона — прогон доходит до конца как обычно. Ctrl+C в терминале прогона окно не закрывает. `tero hud` — окно снова открыто на том же прогоне.
5. Второй `tero go` — то же окно переключается на новый прогон, второго окна нет; если первый ещё идёт — метка «+1».
6. Окно появляется сразу после `tero go` и показывает стартовые проверки; провал старта (например, грязное дерево) виден в HUD с причиной и не появляется в `tero history`. `tero go --no-menu` из агента на этом маке тоже открывает HUD.
7. Первый `tero go` в свежем клоне (без `.tero/` в exclude) стартует нормально — и с HUD, и с `--no-hud`.
8. Стоп (например, `stuck`) — ❓ и причина. `kill -9` процесса прогона — HUD показывает «прогон оборвался».
9. Без `pywebview`, по SSH и с `--no-hud` прогон работает как раньше; у процесса HUD нет слушающих сокетов; все существующие тесты зелёные.

# ЧАСТЬ B. ПУЛЬТ

# tero-пульт: живой прогон, решения с телефона

Дата: 2026-10-21. Статус: черновик на одобрение. Прошёл проверку строителем и три волны критиков (GLM 5.3 flash, Gemini 3.8 flash, Muse$ contributor).

## Зачем

Сейчас tero запускает человек в терминале. Любой стоп (`user`, `stuck`, `fuse`, `provider_unavailable`, `secrets`) — это `exit 2` и тишина: вопрос judge остался в терминале, его никто не читает, прогон мёртв.

Хотим:

- tero запускает **LLM-агент**, внутри которого tero живёт как подпроцесс — Claude Code, Muse, opencode, что угодно. Этот агент и есть «мозг»: он может решать.
- tero **никогда не умирает молча**. Любая проблема — это вопрос: сначала Темирлану (на телефон), если он молчит — агенту, если нет и агента — безопасное решение по умолчанию. **Цель — всегда доработать до конца.**
- Темирлан видит статус и **может принять любое решение с телефона**. Тогда у него контроль, а LLM спит и не тратит токены.

## Цели

1. Прогон, который можно запустить в фоне и оставить: `tero go --detach`.
2. Любой стоп внутри прогона становится **точкой решения** (пауза + вопрос), а не выходом.
3. Решает человек с телефона; не ответил за таймаут — агент-хозяин; нет и агента — автопилот (безопасное действие по умолчанию).
4. Падение или зависание процесса не теряет прогон и не плодит двойников; сон машины не убивает живой прогон.
5. Телефон (айфон, без платного Apple Developer): статус на экране блокировки, пуш когда нужен ответ, ответ с телефона.
6. Видно лимиты моделей — насколько их удастся достать.

## Не цели (сейчас)

- Нативное iOS-приложение / Live Activity (нужен Apple Developer $99 — не платим). Поэтому ответ с телефона = тап по пушу → страница → кнопка; кнопок прямо в пуше и в виджете нет.
- Telegram-бот — не нужен.
- Отдельная роль «мозг» внутри tero — мозг это хозяин-агент, не новая роль.
- Параллельные прогоны (одна машина — один активный прогон на репо).
- Сквозное шифрование данных в ретрансляторе (ретранслятор в своём аккаунте Cloudflare; можно добавить позже).
- Очки, браслет Xiaomi (взлом через Gadgetbridge — это Android), Android вообще. Делаются позже поверх того же ретранслятора.

## Анти-цели (провал, даже если «работает»)

- tero упал или завис, и никто не узнал.
- Два процесса tero одновременно работают с одним репо; или живой прогон убит как «мёртвый».
- Агент тратит токены, опрашивая tero в цикле.
- Телефон вибрирует на каждый раунд или повторяет одну и ту же тревогу — пуши выключат через день.
- Пропущенный шаг пропал бесследно; автопилот «проходит» весь план пропусками.
- Телефон или ретранслятор могут выполнить произвольную команду на машине. С телефона — только фиксированный набор действий и текстовый ответ.
- В ретранслятор уходят секреты или код.
- Текст с телефона переписывает правила для моделей (judge ставит SHIP «потому что так сказали»).
- Каждый раз вводить пароль.

## Как это устроено

```
 хозяин-агент (мозг)                 машина с tero (Meta VM / мак)
 Claude Code / Muse / opencode
   │  tero go --detach  ───────────▶  tero (фоновый процесс-владелец, держит flock)
   │  tero wait (фоном) — спит        │  state.json (пишет только владелец) + pulse
   │                                  │  точка решения → ждёт человека
   │  ◀── wait вышел: 3/5/0/4/2/6     │  ответы ← inbox/ (локально и из ретранслятора)
   │  tero status / answer / resume   │  (запасной путь: wake_command будит агента сам)
                                      ▼ только исходящие запросы
                           ретранслятор (Cloudflare Worker + D1, бесплатно)
                           состояние · вопросы · ответы · web push · cron «нет связи»
                                      ▲
                 телефон: страница-пульт (PWA на экране Домой, пуши)
                          + виджет Scriptable на экране блокировки (только чтение)
```

Уровни решения: **человек → агент → автопилот**.

### 1. Ядро tero

**Команды.**

- `tero go --detach` — стартовые проверки как сейчас; `--detach` подразумевает `--no-menu`. Ошибки старта — код 1 сразу, агент в этот момент не спит. Потом уходит в фон отдельным процессом (новая сессия, переживает закрытие агента), печатает id прогона, путь к `state.json` и протокол агента, возвращается. На macOS оборачивает себя в `caffeinate -i`, чтобы машина не засыпала от простоя.
- `tero go` без `--detach` — то же на переднем плане: печатает вопросы и ждёт ответа (с телефона или `tero answer` из другого терминала). Коды выхода — как сейчас: `0`, `1`, `2` (`stop`), `130`, плюс `4` «готово с долгом». Кодов `3/5/6` у `go` нет — он на паузе не выходит.
- `tero wait [--timeout S]` — **то, чем агент спит.** Блокирует, пока не нужен агент, и выходит с кодом:
  - `0` — готово чисто; `4` — готово с долгом; `2` — остановлен;
  - `3` — нужно решение агента (`waiting_agent`);
  - `5` — прогон мёртв или завис (см. «Пульс»), нужен `resume`;
  - `6` — истёк `--timeout`, ничего не случилось.
  `wait` сначала смотрит статус: `done`/`stopped` → `0`/`4`/`2`, даже если процесса уже нет; `5` — только при незавершённом статусе. Пока `wait` работает и после его выхода, он держит **аренду агента** (см. «Агент на связи»).
- `tero status [--json]` — фаза i/n, раунд, кто работает (роль, провайдер, модель), статус, открытый вопрос (id, текст, допустимые действия), журнал решений, долг, лимиты, возраст пульса, есть ли агент на связи, жив ли пуш-канал телефона.
- `tero answer <id> <действие> [текст] --why "…"` — ответ на вопрос. Кладёт файл в `inbox/`, ждёт, пока владелец примет или отклонит, печатает результат. Локальный `tero answer` — это **агент**; человек — телефон или `tero answer --human` в интерактивном терминале (stdin — TTY).
- `tero resume` — поднять мёртвый или зависший прогон.
- `tero stop` — остановить в любой момент (см. «Стоп во время шага»).
- `tero notify "текст"` — сообщение на телефон (часовой отчёт агента).
- `tero guide` — протокол агента.
- `tero pair` / `tero relay setup` — см. «Ретранслятор».

**Один владелец.** Прогоном владеет ровно один процесс: при старте и `resume` он берёт эксклюзивный `flock` на `.tero/run.lock` и пишет свой pid в `state.json`. Не взял лок — выходит. Только владелец пишет `state.json`; запись атомарная (временный файл + rename). Все остальные пишут только в `inbox/`: по файлу на ответ, с UUID, атомарно. Владелец применяет ответ и **в той же атомарной записи `state.json`** фиксирует эффект, списание бюджета и UUID как применённый; потом пишет `inbox/<uuid>.result` («принято» / «отклонено: уже отвечено …» / «отклонено: действие недопустимо»). При `resume` применённые UUID повторно не применяются.

**Состояние на диске.** В папке прогона:
- `state.json` — статус (`running` / `waiting_human` / `waiting_agent` / `waiting_limit` / `done` / `stopped`), pid, фаза, раунд, текущая роль, sha чекпоинта текущей фазы, открытый вопрос, журнал решений (кто, что, почему, когда), применённые UUID, долг, бюджет продолжений, счётчик пропусков подряд у автопилота, лимиты, разрешённые пути-«секреты».
- `pulse` — `alive` (поток пульса, раз в 30 с) и `progress` (главный цикл, после каждого **завершённого** шага; в ожидании — после каждой завершённой итерации опроса с сетевым таймаутом ≤ 10 с).
- `lease` — аренда агента; `watch` — когда `wait` впервые увидел текущее значение `progress` (id загрузки системы + монотонное время), чтобы зависание считалось и через цепочку коротких `wait --timeout`; `inbox/`; `ledger.jsonl` (как сейчас).
- В точке решения дополнительно: sha дерева (`git write-tree` с неотслеживаемыми файлами) — чтобы после краша вернуть ожидание с тем же деревом.

**Пульс.** Отдельный поток (не asyncio-задача: тест-гейт и git в нынешнем коде блокируют event loop, `src/loop/phase.py:_gate`). Решения о «смерти» принимает `wait` по **своему монотонному времени** (на macOS оно стоит во время сна — сон машины не выглядит как смерть):
- **мёртв** — pid не существует (и `flock` свободен — `wait` проверяет неблокирующей попыткой);
- **завис** — pid жив, но `progress` не менялся дольше, чем самый длинный таймаут роли/гейта + 5 мин (в шаге) или 2 мин (в ожидании), считая по системному монотонному времени от отметки в `watch`; или `alive` не менялся 10 мин монотонного времени (умер поток пульса).
В обоих случаях `wait` → `5`. Устаревший `alive` сам по себе (без этих условий) — не смерть.

**Точки решения вместо стопов.** Каждый нынешний `_halt(...)` в `src/loop/phase.py` превращается в точку решения:

| сейчас | вопрос | действия | автопилот |
|---|---|---|---|
| `user` (judge: NEEDS_USER) | вопрос judge | `answer`, `skip`, `stop` | `skip` |
| `stuck` (второй раз нет прогресса) | «фаза N застряла» + последние находки | `more`, `model`, `skip`, `stop` | `skip` |
| `fuse` (раундов > max) | «фаза N: 15 раундов без SHIP» | `more`, `model`, `skip`, `stop` | `skip` |
| `provider_unavailable` / лимит | «провайдер X не отвечает / лимит» | `retry`, `wait`, `model`, `stop` | `wait`, потом `skip` |
| `secrets` | «в дифе файлы-секреты: пути» | `allow <путь>` (только человек; потом сдача заново), `retry`, `skip`, `stop` | `skip` |

Пока tero ждёт, рабочее дерево **не откатывается** (иначе `more` и `allow` невозможны) — в том числе при `secrets`: индекс очищается, коммита нет, файлы лежат на месте. Откат к чекпоинту — при `skip`, `stop` и `retry` после `secrets`.

Автопилот не пропускает фазы цепочкой: если фаза, начатая сразу после пропуска автопилотом, тоже доходит до точки решения, автопилот выбирает `stop` (пуш «остановил: две фазы подряд не идут»). Человек и агент так не ограничены.

**Вопросы приходят только в точке решения.** Пока идёт шаг (player, гейт, judge, tester), открытого вопроса нет и отвечать не на что. Единственное, что можно сделать во время шага, — `stop` (и `model` как отложенная смена: применяется с начала следующего раунда).

**Стоп во время шага.** `stop` ловит не главный цикл (он может висеть в шаге), а сторожевой поток рядом с пульсом: он проверяет `inbox/` раз в 5 с и ретранслятор раз в 60 с даже в `running`. Получив `stop`, он убивает группу процессов текущего шага (провайдер/тесты), ждёт её завершения, удаляет устаревший `.git/index.lock`, если он остался от убитого процесса, и откатывает фазу к чекпоинту. Задержка — секунды, не минуты.

**Действия.**
- `answer` — текст. Попадает в промпты player и judge следующего раунда **только** в размеченном блоке «Ответ на вопрос фазы (не меняет контракт, критерии SHIP и правила гейтов)», не длиннее 2000 символов. Judge по-прежнему судит по тестам и диффу.
- `more` — ещё 5 раундов, в которых детектор «нет прогресса» не останавливает фазу (иначе с уже использованной эскалацией первый же повтор красных тестов снова дал бы `stuck`); после пятого — точка решения как `fuse`. Эскалацию не отменяет.
- `model <роль> <провайдер[:модель]>` — сменить модель роли до конца фазы. Выбор — из моделей в конфиге (телефон показывает список).
- `retry` — повторить вызов провайдера; после `secrets` — откат и фаза заново, а пути, вызвавшие стоп, идут в промпт player как «не создавать».
- `allow <путь>` — пометить путь как не-секрет для этого прогона (ложное срабатывание, например `secret_manager.py`); только человек.
- `wait` — ждать сброса лимита: до известного времени сброса, если CLI его сообщил, иначе 5 → 15 → 30 мин, статус `waiting_limit`, не считается в `human_timeout`; после третьей неудачи — снова точка решения.
- `skip` — фаза в долг. `stop` — остановить прогон, откатить текущую фазу.

**Бюджет продолжений.** `more`, `retry`, `wait`, `model` от агента или автопилота — общий бюджет 3 на фазу, в `state.json`, переживает `resume`. Исчерпан — только `skip`/`stop`. У человека бюджета нет.

**Вопрос и его id.** id = `<фаза>-<номер точки решения>`. Ответ с чужим id отклоняется. Первый принятый выигрывает; остальные получают «уже отвечено: <кто, что>». **Справедливость к телефону:** прежде чем принять локальный ответ агента, владелец синхронно опрашивает ретранслятор; если там есть ответ человека на этот id — выигрывает человек, без сравнения часов.

**Агент на связи (аренда).** `tero wait` пишет в `lease` срок: пока ждёт — «сейчас + 2 мин», продлевая каждые 30 с; при выходе с `3` — «сейчас + `agent_timeout`» (30 мин на решение); при выходе с `6` — «сейчас + 5 мин» (на повторный вызов). Агент на связи, пока аренда не истекла. Ответ агента или новый `wait` продлевают её.

**Ожидание.**
1. Точка решения → `waiting_human`, вопрос уходит в ретранслятор (пуш); владелец опрашивает `inbox/` и ретранслятор раз в 10 с.
2. Нет ответа за `human_timeout` (15 мин) → `waiting_agent`; `wait` агента выходит с `3`. Вопрос **остаётся открытым** для человека.
3. Аренда агента истекла (агента нет или он не ответил за 30 мин) → пуш «агента нет, решу сам через 15 мин» → через 15 мин **автопилот** (таблица, бюджет, правило «не цепочкой»), запись «решил автопилот».
4. Нет ретранслятора → шаг 1 пропускается. Нет ни ретранслятора, ни аренды агента → автопилот через 10 мин.
5. **Будильник `wake_command`** (для хозяев без фоновой команды). Запускается только когда аренда агента **истекла** — иначе получится второй агент рядом с живым; один раз на вопрос. Это свежий агент без старого контекста, например `claude -p --permission-mode … "Ты мозг tero. Выполни: tero guide; tero status --json --run {run_dir}; ответь на вопрос {question_id}"`. Плейсхолдеры `{run_dir}`, `{question_id}`. Запуск даёт аренду на `agent_timeout`; не ответил — шаг 3 (предупреждение и автопилот).

Порядок шага 3 с будильником: аренда истекла → `wake_command` → `agent_timeout` → пуш «агента нет» → 15 мин → автопилот.

**Повторы без шума.** Подряд идущие точки решения по одной причине (провайдер всё молчит) дают не больше одного пуша в 30 мин: «провайдер X всё ещё молчит, попытка k/3».

**Пропуск = долг.** `skip` откатывает фазу к чекпоинту, пишет её в долг (фаза, причина, последние находки, кто решил) и идёт к следующей. Чекбоксы фазы остаются `[ ]` — повторный запуск плана попробует её снова. Финал и телефон показывают долг отдельно; итоговый код `4`.

**Сдача фазы и краш.** Коммит фазы получает трейлер `Tero-Phase: <id прогона>/<номер фазы>`; если фаза не изменила файлов — пустой коммит (`--allow-empty`) с тем же трейлером. Фазы из долга этого прогона при `resume` не запускаются заново. Фаза **сдана тогда и только тогда, когда** в `git log <чекпоинт>..HEAD` есть коммит с её трейлером — не по чекбоксам плана (план может лежать вне репо, а чекбокс ставится до коммита).

**Возобновление** (`tero resume`, после `wait` → `5`):
1. Если старый pid жив (завис) — убить его группу процессов, дождаться освобождения лока. Если pid жив, а условия «завис» не выполнены — отказать («прогон жив»).
2. Взять лок. Убрать устаревший `.git/index.lock` (владелец мёртв, git-процессов прогона нет).
3. Коммит с трейлером текущей фазы есть → фаза сдана, состояние догоняет git (и чекбоксы в плане вне репо выставляются). Нет, но прогон умер **в точке решения** и дерево совпадает с записанным sha → ожидание восстанавливается как было (тот же раунд, тот же вопрос). Иначе → откат к чекпоинту из `state.json` (вместе с чекбоксами плана) и фаза заново.
   Счётчик крашей подряд в одной фазе: на третьем `resume` отказывает, прогон → `stopped`, пуш «фаза N падает при каждом запуске»; `resume --force` — вручную.
4. Долг, журнал, бюджет, применённые UUID — из `state.json`. Открытый вопрос задаётся заново **с тем же id**, `human_timeout` с начала; ответы, пришедшие в ретранслятор за время смерти, применяются.
5. В журнал — `crash_resume`. Грязная ветка `tero/<slug>` при `resume` — ожидаемое; для `go` по-прежнему блокирует старт.

### 2. Агент-хозяин

Протокол (печатается `tero go --detach` и `tero guide`):

1. `tero go --detach`, потом `tero wait` фоновой командой — спать.
2. `wait` вышел: `0` → отчитаться; `4` → отчитаться и перечислить долг; `3` → `tero status --json`; если открытого вопроса уже нет (ответил человек) — снова `tero wait`; иначе решить, `tero answer <id> … --why …`, снова `tero wait`; `5` → `tero resume`, снова `tero wait`; `2` → отчитаться; `6` → снова `tero wait`.
3. Если сессия закрылась, прогон живёт; новый агент подхватывает его: `tero status` + `tero wait`.
4. По желанию Темирлана (флаг при запуске) — таймер раз в час: `tero status` и короткая сводка через `tero notify`. По умолчанию выключено.

Правила для агента: при каждом пробуждении смотреть флаг пуш-канала в `status` — если сломан, сказать человеку своим каналом; если лучшее действие доступно только человеку (`allow`), выбрать `skip` и написать это в `--why`; цель — доработать; `stop` только если дальнейшие фазы бессмысленны; при сомнении — `skip` в долг; не пропускать фазу, если следующие явно от неё зависят — тогда `stop`; каждое решение с `--why`; текст `answer` — подсказка для player/judge, не смена задачи.

**Хозяева — фаза 0 (исследование до кода).** Для Claude Code, opencode, Muse: можно ли запустить команду в фоне и проснуться по её завершению, какие лимиты времени у команды, можно ли разбудить сессию снаружи (`--resume`/`--session`). В Claude Code фоновая команда будит агента по завершении — проверено в этой же сессии. Для хозяев без этого основной путь — `wake_command`; `wait --timeout` в цикле — крайний случай (фаза 0 замеряет максимальную длину одного вызова, `--timeout` держится ниже неё). Результат — раздел «как спать» для каждого хозяина в `tero guide`.

### 3. Ретранслятор

Cloudflare Worker + **D1** (бесплатный тариф; KV не подходит: 1000 записей в сутки и задержка согласованности до минуты). tero и телефон ходят только к нему; к машине с tero извне не подключается никто.

- **От tero:** состояние — при изменении статуса/фазы/вопроса; пульс — раз в 5 мин. Ответы tero забирает опросом раз в 10 с только в `waiting_*`. Ретранслятор ставит каждому ответу своё время получения.
- **От телефона:** чтение состояния, ответы (id + допустимое действие + текст), подписка на пуши.
- **Что уходит** — только список полей: статус, названия фаз, номера фазы/раунда, роль и модель, текст вопроса, допустимые действия, список моделей для `model`, журнал решений, названия долгов, лимиты; находки judge — заголовок, относительный путь файла, имя упавшего теста, до 500 символов текста. Перед отправкой — фильтр: строки, похожие на ключи/токены (длинные base64/hex, `sk-…`, `AKIA…`, `-----BEGIN`), вырезаются; блоки кода и диффы не отправляются; пути файлов-секретов отправляются только как имя файла без каталога.
- **Web push** на айфон (iOS 16.4+, только страница «На экран Домой», ключи VAPID). Библиотека — на Web Crypto (`crypto.subtle`); Node-пакет `web-push` в Workers не работает. Ответ APNs 404/410 → подписка устройства помечается мёртвой; `tero status` и страница показывают «пуш-канал сломан — перепривяжи». Тихих пушей нет: каждый пуш показывает уведомление. Текст пуша — до 200 символов + «подробно — в пульте»; полный текст только на странице. VAPID: ключи P-256, `aud` — origin эндпоинта, `exp` ≤ 24 ч; код ответа push-сервиса пишется в D1 для диагностики. План Б, если шифрование не влезет в CPU: пуш с общим текстом «tero: нужен ответ» без данных.
- **Cron** раз в 5 мин: активный прогон — по фиксированному ключу; пульс старше 15 мин при незавершённом статусе → **один** пуш «нет связи с машиной (сон, сеть или краш)», отметка `stale_notified` до возвращения пульса. Завершение (`done`/`stopped`) tero отправляет всегда.
- **CPU-лимит** бесплатного Worker'а — 10 мс на вызов. Приёмка фазы 2 включает замер цепочки «принять состояние → отфильтровать → отправить пуш»; не влезает — менять библиотеку, не тариф.

**Привязка без пароля.** `tero pair` печатает QR и ссылку с одноразовым кодом (живёт 15 мин, сгорает при обмене). Страница в Safari говорит «добавь на экран Домой». Хранилища Safari и PWA на iOS раздельные, поэтому манифест генерируется Worker'ом с кодом в `start_url`; при первом запуске PWA обменивает код на токен устройства и показывает кнопку **«Включить пуши»** — `requestPermission()` вызывается только из её нажатия (iOS иначе молча отказывает). Манифест: `display: standalone`, `start_url` и `scope` — корень, иконки; service worker в корне; приёмка проверяет, что подписка создана из режима standalone. Отозванный токен → PWA показывает «привязка недействительна» и поле для нового кода. Токены — по одному на устройство, хранятся в D1 хешем, отзываются по одному (`tero pair --revoke <устройство>`); `--reset` отзывает все; `tero pair` без аргументов — новая ссылка. `stop` с телефона — с подтверждением.

**Риск, принятый осознанно.** Токен устройства даёт право писать текст, который попадёт в промпт player, а player работает с shell. Значит, токен устройства — секрет уровня пароля. Защита: токены на устройство с отзывом, текстовые ответы — только с токена PWA (не виджета), лимит длины, всё видно в журнале; настройка `phone_text_answers: false` оставляет телефону только кнопки.

**Развёртывание.** Один раз: `tero relay setup` генерирует ключ записи и ключи VAPID, создаёт D1, кладёт секреты через `wrangler secret`, деплоит Worker, пишет адрес в `~/.tero/config.yaml` (секция `relay`) и ключ записи в `~/.tero/secrets.env`. Нужен бесплатный аккаунт Cloudflare и один раз `wrangler login` — делает Темирлан (согласен). Приёмка фаз 2–3: автотесты на `wrangler dev` (cron — через `--test-scheduled`) + прогон cron и пуша на задеплоенном Worker'е с тестовым прогоном + замер CPU + ручная проверка Темирланом на айфоне по чек-листу (привязка из Safari в PWA, кнопка пушей, пуш пришёл, ответ дошёл до прогона, виджет показывает статус, «нет связи» пришёл один раз).

**Уровни шума.** Пуш: вопрос; «агента нет — скоро решу сам»; решение агента/автопилота; нет связи (один раз); прогон закончен; часовой отчёт (если включён). Без пуша: раунды, вызовы моделей.

### 4. Телефон

- **Страница-пульт** (JS, PWA, отдаётся Worker'ом; обновляет состояние раз в 15 с, только пока открыта). Корень **всегда** показывает открытый вопрос первым (тап по пушу на iOS надёжно открывает только корень — глубоких ссылок не обещаем): текст, кнопки допустимых действий, поле текста, список моделей для `model`. Дальше: статус, фаза i/n, раунд, кто работает, лимиты, «уже отвечено: …», журнал решений, долг, история, состояние пуш-канала.
- **Виджет Scriptable** (JS, файл в репо, **без токена в коде**). Токен — отдельный, **только для чтения**: страница-пульт показывает его для копирования, его вставляют в параметр виджета (`args.widgetParameter`). На экране блокировки — прямоугольный формат, 2–3 короткие строки (`2/5 · р3` / `⚠ ответ` / `лимит 40%`), **только взглянуть** — переход по тапу с экрана блокировки не обещаем (проверить на айфоне в фазе 3); на домашнем — подробнее, тап открывает страницу в Safari (iOS не открывает PWA по ссылке) — там без токена PWA видно только чтение и подсказка «ответить — в приложении с экрана Домой». Обновляется, когда разрешит iOS (обычно раз в 15–60 мин) — виджет для фона, срочное — пуш.

## Решения, которые принял я (Claude), не Темирлан

- Пробуждение агента через фоновый `tero wait` (коды 0/2/3/4/5/6) + запасной `wake_command`; прогон — отдельный процесс-владелец под `flock`; у `go` коды прежние + `4`.
- «Мёртв» — только pid нет и лок свободен; «завис» — по монотонному времени `wait`; сон машины не смерть; на маке `caffeinate`.
- Аренда агента вместо проверки pid `wait`; автопилот после истечения аренды + 15 мин предупреждения; без ретранслятора и агента — 10 мин.
- Автопилот не пропускает фазы цепочкой — вторая подряд проблемная фаза → `stop`.
- Бюджет продолжений 3 на фазу для агента и автопилота; `more` = 5 раундов, эскалацию не отменяет.
- Локальный `tero answer` = агент; человек = телефон или `--human` в TTY; при гонке человек выигрывает по времени получения ретранслятором.
- Во время шага вопросов нет; `stop` убивает шаг сразу, `model` — со следующего раунда.
- Сдача фазы — по git-трейлеру `Tero-Phase`, не по чекбоксам.
- `allow <путь>` для ложных секретов — только человек; при `retry` после `secrets` пути идут в промпт как «не создавать».
- D1 вместо KV; список полей + фильтр; относительные пути и имена тестов можно, код и диффы — нет; «нет связи» — один пуш через 15 мин.
- Ответ с телефона в промпте только в размеченном блоке, ≤ 2000 символов; `phone_text_answers` можно выключить.
- Токены по одному на устройство; виджету — отдельный токен только для чтения через `widgetParameter`; пуши — по кнопке.
- `secrets` не откатывает дерево до решения; краш в точке решения восстанавливает ожидание по sha дерева.
- `more` = 5 раундов без остановки по «нет прогресса».
- `wake_command` — только при истёкшей аренде, свежий агент без контекста, один раз на вопрос.
- Сторожевой поток принимает `stop` во время зависшего шага.
- Три краша подряд в фазе → `stopped`; пустые фазы — пустой коммит с трейлером; долг при `resume` не перезапускается.
- Пуш ≤ 200 символов; повторы одной причины — не чаще раза в 30 мин; код привязки 15 мин; виджет блокировки только для взгляда.
- Пульс 30 с; `human_timeout` 15 мин, `agent_timeout` 30 мин — в конфиге.

# ЧАСТЬ C. ОТКАЗОУСТОЙЧИВОСТЬ

# tero: отказоустойчивость, agy, экзамен судей (будущая работа)

Дата: 2026-10-22, правка после волны 1 критиков (Gemini, GLM). Решения Temirlan. Делать ПОСЛЕ прогонов
«Двора», в отдельной копии (worktree), чтобы не менять правила посреди сравнения. Каждый сбой воспроизвести
тестом red→green. Пометка *(моё)* — решение Claude, его можно оспорить.

## Главный принцип

**Работа исполнителя никогда не выбрасывается.** Сейчас любая остановка фазы делает `rollback`
(`src/loop/git.py:84`, вызовы `phase.py:700`, `:730`) — всё написанное стирается. В «Дворе»
так потеряны: фаза 7 у C1 (код был готов, судья спросил NEEDS_USER), фаза 7 у A1 (27 минут).

## 0. Снимок работы (общий механизм для п.1 и п.2) *(моё, по критике)*

- **Когда:** при каждом выходе исполнителя (успех, таймаут, падение, kill), при входе в судью и перед любым
  откатом. Не только «перед откатом»: иначе судья, упавший без отката, ничего не оставляет.
- **Как:** сантехническими командами, без рабочего индекса: временный `GIT_INDEX_FILE`, `git add` отслеживаемых
  и новых не игнорируемых файлов, `write-tree`, `commit-tree`, `update-ref refs/tero/phase-N-roundK`. Так
  зависший `.git/index.lock` от убитого процесса не мешает. Перед снимком проверить, что PID исполнителя мёртв.
- **Что не попадает:** всё из `.gitignore` и deny-list (`.env`, ключи, `node_modules`, `.tero/`). Тест:
  в ref нет путей из deny-list.
- **Неизменяемость:** судья и `resume` работают ТОЛЬКО с ref (`base..ref`), никогда с живым деревом. Что бы
  ни случилось с деревом между падением и resume, судят тот же код. ref и base пишутся в `state.json` и ledger.
- Рабочее дерево после падения исполнителя не трогаем, пока ref не записан и не проверен (`git cat-file -p`).

## 1. Упал / убит исполнитель → новый исполнитель с сохранением прогресса

- Новый исполнитель стартует в НОВОЙ сессии модели (никакого `--continue` для аварийного восстановления:
  история чужой сессии расходится с диском) и получает в промпте: «часть работы уже сделана, вот `git diff
  base..ref`, продолжай, не переписывай готовое».
- Тесты на сыром аварийном снимке НЕ гоняются до раунда нового исполнителя: недописанный код всегда красный.
- Откат к чистой попытке — только после K_max=2 раундов-продолжений подряд, в которых судья не принял и набор
  замечаний не уменьшился. Снимок остаётся в refs для разбора. Считаются только раунды, дошедшие до судьи.
- Тест на моках: stub-исполнитель убит на середине → в промпте stub-исполнителя №2 лежит diff первого
  (проверяем промпт и `git cat-file -p ref`, а не «результат содержит работу»: LLM вправе переписать).

## 2. Упал / ответил не по схеме судья → работу НЕ дропать

- Ответ не по схеме (в т.ч. от `agy --json-schema`) = сбой судьи, как и таймаут.
- В журнале шаг `judge_pending`: «код в `refs/tero/phase-N-roundK`, нужно ревью». Откат не делается.
- `tero go --resume` продолжает **с судьи**: исполнитель не запускается, судья смотрит ref. Флага «начать с
  судьи» сегодня нет — добавить.
- **Модель судьи в рамках прогона не меняется** (убрано «или другая модель»: противоречило экзамену и
  честности A/B). После 3 сбоев подряд — остановка `judge_pending` с текстом «код готов, не принят, вот ref
  и команда `tero review`», не `stuck`. Сменить судью можно только между прогонами.

## 3. Остальное из плана

- Таймаут по зависанию (`stall_timeout_s`: нет вывода N минут), не по часам. Не применять к провайдерам без
  потока (`agy -p` отдаёт ответ целиком в конце): для них только общий таймаут или `--output-format stream-json`.
- Пауза вместо остановки при сетевой ошибке: 1→2→5→10→60 мин, **потолок**: `max_retries` и общий дедлайн
  2 часа на вызов. Ошибки авторизации и квоты (протухший токен `agy`, лимит) — сразу стоп с понятным текстом,
  не ожидание. Сеть отличать от провайдера по коду возврата CLI.
- `TimeoutError` не называть «провайдер недоступен».
- При `--no-escalation` `NEEDS_USER` не принимать: один переспрос судье, затем один свежий судья; третий
  `NEEDS_USER` → `judge_pending` «нужен человек», без бесконечного цикла.
- Неверный формат `config.yaml` (ключи вне `defaults:`) — предупреждение, не молчаливое игнорирование.

## 4. Провайдер `agy` (Antigravity CLI) вместо `gemini`

- Старый CLI `gemini` мёртв (решение Temirlan). Gemini теперь только через `agy` (`~/.local/bin/agy` v1.4.5,
  вход по подписке Google). Проверено 2026-10-22: `agy -p` отвечает, `agy models` отдаёт список.
- **Модели `agy` сегодня** (из `agy models`): `gemini-3.8-flash-high|medium|low`, `claude-sonnet-4-6`,
  `claude-opus-4-6-thinking`, `gpt-oss-120b-medium`. **Gemini 3.1 Pro в списке нет** — дефолт
  `gemini-3.1-pro-preview` из `gemini.py` не переносить. Дефолт для судьи — `gemini-3.8-flash-high` *(моё)*.
  Через `agy` же доступны Claude Sonnet/Opus 4.6 — кандидаты в судьи по подписке Google.
- Флаги: `--print/-p`, `--model`, `--effort low..max`, `--json-schema`, `--output-format text|json|stream-json`,
  `--print-timeout` (формат `900s`, с единицей!), `--continue`, `--conversation`. `--dangerously-skip-permissions`
  только для исполнителя и тестера; **судья получает режим без записи** *(по критике)*.
- Невалидный JSON при `--json-schema` = сбой судьи (п.2), не тихий retry. `--print-timeout` и `stall_timeout_s`:
  побеждает меньший.
- Pre-flight перед очередью: короткий `agy -p` «ок»; нет токена → стоп с просьбой войти, а не зависание на TTY.
  Параллельные `agy` могут делить файлы профиля — в одном прогоне не более одного вызова `agy` одновременно.
- Старый `gemini`: алиас на `agy` с предупреждением в конфиге (миграция), не молчаливое удаление.
- Тест готовности: `--judge agy:gemini-3.8-flash-high` возвращает валидный вердикт по схеме на stub-диффе.

## 5. Экзамен судей (через `Provider` tero, не ad-hoc скрипт) *(по критике)*

- Кандидаты: `agy` (Gemini 3.8 Flash, Claude Sonnet 4.6), `claude` (Sonnet), `codex`, `opencode` (GLM 5.3
  flash, Muse). Идут через те же классы `Provider`, чтобы мерить судью, а не обёртку.
- Два слоя: (1) адаптер — каждый CLI возвращает валидный вердикт на тривиальном диффе; (2) качество.
- Набор: 25–30 диффов (явные баги, тонкие логические, чистые), часть вне «Двора» (holdout). Метки истины —
  два независимых прохода, расхождения разбирает человек. Порог годности фиксируется ДО замеров.
- Мерим: найденные баги, ложные отклонения, ответы не по схеме, время.
- Правило: судья из другой семьи, чем исполнитель. Судью в живом прогоне не менять.

## 6. Стыки с HUD и пультом

- `state.json` получает: `status: judge_pending`, `snapshot_ref`, `base`, причину. HUD показывает «⏸ код ждёт
  ревью» и путь ref, не ❓ и не «упал».
- В пульте `judge_pending` — точка решения: «позвать судью снова / принять вручную / отклонить».
- Порядок работ в сводной спеке: раунд 0 HUD → ядро пульта (state.json, пульс) → отказоустойчивость (эта
  спека) → ретранслятор и телефон.

## Критерии готовности

- Тест: stub-исполнитель убит на середине → `git cat-file -p <ref>` содержит его diff, второй stub получает
  этот diff в промпте.
- Тест: stub-судья вернул мусор → ref есть, дерево нетронуто, `resume` запускает только судью на этом ref.
- Тест: три мусорных ответа судьи подряд → остановка `judge_pending`, не `stuck`.
- Тест на КАЖДЫЙ пункт п.3 (stall, потолок паузы, auth-ошибка без ожидания, `TimeoutError`, `NEEDS_USER` с
  циклом, предупреждение о конфиге) на stub-провайдерах; настоящих LLM в тестах нет.
- Тест: в ref нет путей из deny-list; зависший `index.lock` не мешает снимку.
- Оговорка: `kill -9` самого tero и потеря питания ref не гарантируют; гарантия — для перехватываемых
  сигналов, исключений и смерти дочернего процесса исполнителя.
